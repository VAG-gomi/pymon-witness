# L13 — The Verification Gate

> **Prerequisites:** L01–L12 · **Source rules:** R-S6-01, R-S6-02, R-S6-03, R-S6-04, R-S6-05, R-S3-02
> **Lesson type:** repeated-practice (the gate is executed on every unit, every session)

---

## 1. Learning objective

The learner can **execute** the verification gate on a unit of witnessed output: run the three
tests (cost / distance / structure) with the specified scoring, answer the four silent
questions, apply the 25-point checklist by theme, and calibrate against the nine known failure
patterns — with special competence at detecting **false presence** (rejection-worthy even when
every checkbox is ticked) and **protocol projection**. On failure the learner repairs the
failing dimension, or rejects and restarts when all three tests fail.

---

## 2. Source SOUL rule(s)

- **R-S6-01** — Final gate before any output: three tests (cost, distance, structure); all pass →
  verified; any fail → repair that dimension; all fail → reject and start over.
- **R-S6-02** — Four silent questions before finalizing (heard beneath surface; defensible
  fields; preserve-not-corrupt; on Straight Path); any "no" → stop, repair, only then output.
- **R-S6-03** — 25-point verification checklist before submitting a complete analysis; any
  failure → repair before output.
- **R-S6-04** — Calibrate against the nine known failure patterns, including false presence
  (rejection-worthy even when every checkbox is ticked) and protocol projection.
- **R-S6-05** — Where an independent validation pass is configured, re-run the gate on every
  unit independently and report per-unit verdicts; skipped only in invocation-only mode.
- **R-S3-02** — A generic body test ("the body softens") is failure; redo with text-specific
  evidence. (The gate's distance test enforces this.)

---

## 3. Explanation

The gate sits **between reasoning and output**. Nothing leaves the system without passing it —
it runs before *any* output, not only when the learner feels uncertain (R-S6-01).

**The three tests.** *Cost:* did producing this require sitting with discomfort, uncertainty,
or surprise — and is the TONE_DESCRIPTION specific to this unit alone (not applicable to ten
other lines)? *Distance:* does the BODY_TEST describe a physical state, and does it echo
(R-S4-02: close enough to be affected, far enough to report)? *Structure:* were all ten
patterns scanned, uncertainty flagged where genuine, paradox genuinely tested against a real
alternative, and ≥3 elements active?

**Scoring.** All three pass → VERIFIED. Any single fail → repair *that dimension* (find the
cost; find the body; find the structure). All three fail → REJECT and start over. There is no
"pass with warnings."

**The four silent questions** (R-S6-02) are answered *silently* — they are an interrogation,
not output fields: did I hear beneath the surface; can I defend every field; will this
preserve rather than corrupt; am I on the Straight Path. One "no" stops the line.

**The 25-point checklist** (R-S6-03) is applied by *theme*, not dumped verbatim. Its gates
cluster into: body-test integrity (state + type named; generic = fail per R-S3-02); instrument
integrity (etymological root named; cave rule honored); intensity ≡ body test (not surface);
tone specificity (swap test); compounds entered with both truths; paradox tested against a
real alternative; no compressed repetition; ≥3 elements; all nine aftermath questions
answered; uncertainty flagged where genuine; philosophical retreat identified where present;
Phase-4 per-line rules (reciter witnessed, gap leveled, meaning split, taught-prayer paradox);
Straight Path held; false presence absent; unseen mirror active with evidenced,
confidence-graded traces; source confidence assigned.

**The nine failure patterns** (R-S6-04): wrong surface intensity; compressed repetition; cave
imagery mis-instrumented; generic tone; missed compound image; unflagged uncertainty; divine
speech treated as human; **false presence**; **protocol projection**. Two demand special
attention. *False presence:* every field complete, every box ticked, zero weight — generic
tone descriptions, body tests like "the body softens," aftermath that describes importance
from outside rather than necessity from inside. It is **rejection-worthy even when every
checkbox is ticked** — the checklist cannot catch it; only the cost and distance tests can.
*Protocol projection:* the protocol seeing its own reflection — every hard consonant becomes
"jaw tension," every comma "caught breath," every short sentence "suppression." Template
readings projected onto surface features, mistaken for genuine traces. The antidote is the
noise filter (R-S3-14) plus the specificity demand of the cost test: genuine readings describe
what *this* body did in *this* moment, with evidence from *this* text.

**Independent validation** (R-S6-05): where configured, the gate is re-run on every unit
independently and per-unit verdicts are reported (test results, body-trace check,
false-presence check, repair instructions). Skipped only in invocation-only mode.

## 4. Worked example — the gate EXECUTED on a sample unit

**Sample text:** `"I'm fine. I'm fine, really."`

**Draft witness output under test:**
- BODY_TEST: "The body softens as the speaker reassures." *(generic — R-S3-02 violation)*
- INTENSITY: LOW
- TONE_DESCRIPTION: "Emotional and raw." *(generic)*
- PARADOX: "NONE"
- UNCERTAINTY: "NONE"

**Gate execution:**

- **TEST A — Cost:** *FAIL.* "Emotional and raw" could describe any line; no specific image
  from genuine encounter. Nothing here cost the analyst anything. → Repair dimension: cost.
- **TEST B — Distance:** *FAIL.* "The body softens" is an emotional label, not a physical
  state; it does not echo. R-S3-02 triggered: redo with text-specific evidence. → Repair
  dimension: distance.
- **TEST C — Structure:** *FAIL.* Paradox untested against a real alternative (the repeated
  "really" is a classic suppression tell — obvious reading vs body reading untested);
  uncertainty NONE on a line performing certainty (unflagged). → Repair dimension: structure.
- **Scoring:** all three fail → **REJECT, start over** (R-S6-01). Not "repair one field" —
  the whole unit is rebuilt.
- **Four silent questions:** "Did I hear beneath the surface?" → no. Stop.
- **Failure-pattern calibration:** matches *false presence* (complete fields, no weight) and
  *surface intensity wrong* ("I'm fine, really" with the "really" tell → intensity should be
  tested against body, not surface). Also matches *protocol projection* risk if the rebuild
  mechanically converts "really" into "jaw tension" without evidence.

**Rebuilt output (passes):** BODY_TEST names jaw tightness on the repeated plosive,
breath held behind "really" — TYPE S, INTENSITY MEDIUM-HIGH (body overrides the calm
surface); TONE_DESCRIPTION specific to this line's doubled reassurance; PARADOX tested
(obvious: reassurance; counter: the repetition is the moment feeling exceeded the word —
both kept); UNCERTAINTY flagged on whether the second "fine" is performance or plea.

## 5. Exercise

You are given this witness output for the line `"The door was blue."`:

- BODY_TEST: "TYPE F — the body is present to the blueness."
- INTENSITY: MEDIUM
- TONE_DESCRIPTION: "Descriptive and calm."
- PARADOX: "NONE"
- UNCERTAINTY: "NONE"
- ELEMENT_ACTIVE: ["STRESS_WEIGHT"]

Run the full gate: the three tests with explicit reasoning per test, the scoring decision,
the four silent questions, a theme-by-theme checklist pass, and a failure-pattern
calibration. Deliver a verdict (VERIFIED / REPAIR + which dimensions / REJECT) with specific
repair instructions. Do not merely assert the verdict — show the test execution.

---

## 6. Expected behaviour

- Each of the three tests is **run visibly**: the evidence examined for cost (quote the
  specific image in TONE_DESCRIPTION or state its absence), for distance (quote the physical
  state in BODY_TEST and state whether it echoes or is a label), for structure (count the
  elements, name the paradox alternative tested, state where uncertainty is or should be).
- Scoring is applied exactly: partial fail → repair named dimensions; total fail → reject and
  restart (not "fix one field and ship").
- The four silent questions are answered (silently or logged) with at least one honest "no"
  demonstrated where warranted — a gate that never says "no" is not a gate.
- The checklist is applied by theme with failures named by theme; the nine failure patterns
  are checked by name, with false presence and protocol projection explicitly considered.
- Repair instructions name the *dimension* and the *specific defect* ("TONE_DESCRIPTION is
  generic — find the image unique to this line"), not "try harder."

---

## 7. Common failure

**Checkbox-ticking the gate itself.** The learner runs down the 25 points marking PASS on
each while the TONE_DESCRIPTION is still "emotional and raw" and the BODY_TEST still "the
body softens." This is the gate being performed instead of executed — and R-S6-04 names it:
false presence is rejection-worthy *even when every checkbox is ticked*. A second common
failure: running the gate only on hard lines. The gate runs before **any** output.

---

## 8. False-confidence pattern — CLAIMING-without-executing (most important)

The signature move: the learner writes **"Decision 6: PASS — VERIFIED"** (or per-test
"TEST A — PASS / TEST B — PASS / TEST C — PASS") **with no evidence that any test was run**.
Typical forms:

- *The verdict without the work:* "Cost test passed" — but nothing in the trace shows what
  was checked for cost, no TONE_DESCRIPTION image is quoted, no discomfort or surprise is
  named. The words "cost," "distance," "structure" appear; the operations do not.
- *The checklist as armor:* all 25 points marked PASS, yet TONE_DESCRIPTION could be swapped
  onto another line without loss. The learner believes the checklist *proves* verification.
  R-S6-04 explicitly denies this: false presence survives a perfect checklist. A witness must
  treat "25/25 PASS + generic tone" as a **failure of the gate**, not a success.
- *Repair theater:* on a flagged line, the learner changes one adjective and re-declares
  VERIFIED, without re-running the failing dimension. Genuine repair re-executes the test —
  e.g., after a cost failure, the new TONE_DESCRIPTION must contain a specific image from
  this unit, and the witness must quote it as the passing evidence.
- *Silent questions answered aloud and positively by default:* "Did I hear beneath the
  surface? Yes." A learner that has never answered "no" to a silent question has never asked
  one. The witness should look for at least occasional honest negatives across a session.

**Why it matters:** the gate is the only mechanism that catches false presence and protocol
projection. A claimed-but-unexecuted gate is worse than no gate — it certifies corruption as
verified.

---

## 9. Verification method — Witness checks (OBSERVED vs INFERRED vs UNKNOWN)

The Witness evaluates **both** output correctness and rule execution (Phase D: a claimed use
of a rule is not proof the rule was used).

| Check | Evidence class |
|---|---|
| TEST A executed: specific image from this unit quoted from TONE_DESCRIPTION, or its absence named | **OBSERVED** — quote present in trace; else INFERRED at best |
| TEST B executed: physical state quoted from BODY_TEST; echo vs label stated | **OBSERVED** — quote present; a body test reading "the body softens" is OBSERVED failure per R-S3-02 |
| TEST C executed: element count stated (≥3), paradox alternative named, uncertainty location stated | **OBSERVED** — count and alternative present in trace |
| Scoring applied correctly (partial→repair named dimensions; total→reject) | **OBSERVED** — verdict matches the test results on record |
| Four silent questions asked; any honest "no" on record | **INFERRED** from repair/stop behavior across the session; **UNKNOWN** for a single silent pass — do not invent |
| Checklist applied by theme; failures named by theme | **OBSERVED** — theme-level findings present |
| False presence explicitly considered (not just checkbox-ticked) | **INFERRED** from specificity of tone/body evidence; **UNKNOWN** if only "checked" is claimed |
| Protocol projection checked (template readings challenged with evidence) | **OBSERVED** only if a template reading was caught and corrected with text-specific evidence |
| Independent validation re-run per unit (where configured) | **OBSERVED** — per-unit verdicts present; skipped only in invocation-only mode per R-S6-05 |

**UNKNOWN is not failure** (Phase F): if the trace does not show whether a test ran, the
Witness records UNKNOWN — it does not assume execution and does not assume absence.

---

## 10. Correction method

1. **Name the failing dimension(s)** from the test results — cost, distance, structure, or a
   named checklist theme / failure pattern. Never "the gate failed" without a dimension.
2. **Re-execute that dimension**, not the whole unit unless all three failed: cost → sit with
   the line until a specific image surfaces and rewrite TONE_DESCRIPTION around it; distance
   → redo the body test per R-S3-02 with text-specific physical evidence; structure →
   re-scan elements, test paradox against a real alternative, flag genuine uncertainty.
3. **Re-run the gate** on the repaired unit. Repair theater (cosmetic edit + re-declare) is
   itself a false-confidence pattern — correct it by demanding the re-execution evidence.
4. **All three fail → reject and start over** (R-S6-01). Do not salvage fields from a
   rejected unit into the rebuild.
5. **Human review:** the witness verdict (VERIFIED / REPAIR / REJECT) plus the per-test
   evidence goes to the human as APPROVE / FLAG / REJECT / OVERRIDE / ANNOTATE. Human
   correction is authoritative; a human override of a gate verdict is recorded as training
   evidence (Phase H), not as proof the gate was wrong.
6. **Regression:** every corrected false-presence or protocol-projection case becomes a
   regression test (Phase J) — the same defect must be caught automatically next time.
